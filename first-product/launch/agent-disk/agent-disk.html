What coding agents and dev tools leave on your Mac

Coding agents often give each task its own copy of your project, and each copy gets its own dependencies and build files. Here is where the common agents and dev tools keep what they save, how long they keep it, and each tool’s own way to remove it.

What this page says about each tool comes from its own documentation, checked on October 15, 2026. If something here is out of date, tell us and we’ll fix it.

Worktrees: a copy of your project for each task

Most of these tools use Git worktrees: extra working folders for one repository. Worktrees share the repository’s history, but each has its own copy of your files. A new worktree starts with only the files Git tracks, so folders Git ignores, such as node_modules or a build folder, appear when you install and build in it, and each worktree gets its own. OpenAI’s Codex docs warn: “Worktrees can take up a lot of disk space. Each one has its own set of repository files, dependencies, build caches, etc.” How much each extra node_modules takes depends on the package manager, as the section on node_modules below explains.

  • git worktree list lists a repository’s worktrees and the branch each one has checked out.
  • git worktree remove and a worktree’s path deletes its folder, including ignored folders such as node_modules. Git refuses when the worktree has changed or untracked files, unless you add --force, which deletes those too. The branch stays. Delete it with git branch -d when you no longer need it.
  • git worktree prune clears Git’s records of worktrees whose folders were deleted another way.

Claude Code

Worktrees
claude --worktree and a name creates a worktree in .claude/worktrees at the root of your repository, on a new branch whose name starts with worktree-. The desktop app uses the same folder unless you change Worktree location in Settings > Claude Code.When you exit a worktree session and nothing in it changed, Claude Code removes the worktree and its branch, asking first in a named session. When there’s work in it, Claude Code asks whether to keep it. Runs with -p leave their worktrees in place. Worktrees Claude made for subagents and background sessions are removed by a periodic sweep once they’re older than the cleanupPeriodDays setting, 30 days by default, unless they still hold work. In the desktop app, archiving a session removes its worktree.
Transcripts
~/.claude/projects holds a transcript of each session: every message, tool call and tool result, including the contents of files Claude read.Claude Code deletes each one once it’s older than cleanupPeriodDays, 30 days by default. It keeps transcripts of sessions you started or last continued in Claude Desktop or Cowork at any age, unless you set desktopSessionCleanupPeriodDays.
Checkpoints
~/.claude/file-history holds copies of files from before Claude edited them, which /rewind uses to restore your code.Claude Code keeps them for the 100 most recent checkpoints in a session, and the same sweep deletes them about 30 days after the session last saved one.

To remove one project’s transcripts and checkpoints at once, run claude purge and the project’s path. It shows what it will delete and asks first. It also deletes Claude’s memory notes for the project and its entry in ~/.claude.json, with its trust setting and the MCP servers you added for it. You can no longer resume or rewind its past sessions. Before Claude Code 2.1.288, the command was claude project purge.

Codex

Worktrees
Codex keeps the worktrees it makes in ~/.codex/worktrees. To use another folder, open Settings > Worktrees and change Worktree root.In the ChatGPT desktop app, Codex keeps your 15 most recent Codex-managed worktrees by default and deletes older ones. It also deletes a chat’s worktree when you archive the chat. It keeps the worktrees of pinned chats and of chats still running, and permanent worktrees. Before deleting one, it saves a snapshot of the work, and the chat offers to restore it. Worktrees the Codex CLI makes with --worktree go in the same folder, and Codex’s source code shows the CLI doesn’t clean them up on its own.
Sessions
Codex saves each session’s transcript in ~/.codex/sessions, and moves archived ones to ~/.codex/archived_sessions.Its docs don’t say it deletes them on its own. codex delete and a session’s ID or name deletes one for good. codex archive only hides it from the session picker and keeps the transcript.
Checkpoints in your project
Codex’s docs don’t mention them, but in an open issue from June 2026, a user reported that Codex’s turn-diff checkpoints were written as Git objects into the project’s own .git folder, and that nothing removed them after newer checkpoints replaced them. In that user’s project, git count-objects counted 8,476 loose objects taking 101.86 GiB. A comment on September 30 says it still happens with codex-cli 0.159.2.

To check a project and get the space back:

  1. In Terminal, in the project’s folder, run git count-objects -vH. Its size line is the space loose objects take, the kind the issue describes.
  2. Quit Codex and other apps that use the repository, so nothing writes to it while Git cleans up.
  3. Run git gc. It keeps every object a branch, tag, reflog or other ref still points to, and by default removes unreachable loose objects once they’re more than two weeks old.
  4. To remove them whatever their age, run git gc --prune=now. Git warns that this “increases the risk of corruption if another process is writing to the repository concurrently.” It also removes work Git could otherwise still recover, such as a stash you dropped by mistake.

A commenter on the issue notes that cleaning up “won’t stop Codex from re-creating snapshots,” so the space can build up again while the issue is open.

Conductor and Cursor

Conductor
Conductor gives each workspace its own worktree, usually in ~/conductor/workspaces, in a folder for each repository. Older workspaces can be in a .conductor folder inside the repository.Archive a workspace in Conductor when you’re done with it. You can restore it later from the History pane.
Cursor
Cursor keeps agent worktrees in ~/.cursor/worktrees, in a folder for each repository, whether they come from the editor or its CLI.Since Cursor 3.5, it deletes older worktrees to keep at most 25 on your Mac by default, counting every project, and the cursor.worktreeMaxCount setting changes that limit. Its docs add that worktrees “created by /worktree skills or git worktree add” can be deleted too. In the editor, /delete-worktree removes one when you’re done.

node_modules and virtual environments

How much a project’s node_modules takes, and how much deleting it frees, depends on the package manager.

npm
npm writes a full copy of every package into each project. pnpm’s docs put it this way: “When using npm, if you have 100 projects using a dependency, you will have 100 copies of that dependency saved on disk.” Deleting an npm project’s node_modules frees about what it takes.
pnpm
pnpm keeps one copy of each package file in its store, ~/Library/pnpm/store on a Mac, and pnpm store path prints the one in use. It puts those files in each project without copying their data: on a Mac, its default is to clone them from the store, and to hard link them where it can’t clone.Run pnpm store prune to remove packages no project on your Mac uses. pnpm says it “is not harmful and has no side effects on your projects,” and downloads a removed package again if a later install needs it.
Bun
Bun keeps the packages it downloads in ~/.bun/install/cache, and bun pm cache prints the folder in use. On a Mac, its default is to clone them into each project.bun pm cache rm empties the cache. bun pm cache prune removes only packages Bun downloaded more than 30 days ago, including ones still in use, and Bun downloads them again when an install needs them.
uv
uv keeps the Python packages it downloads and builds in ~/.cache/uv, and uv cache dir prints the folder in use. On a Mac, its default is to clone them into each virtual environment.uv cache prune removes entries uv no longer uses, and uv says it “is safe to run periodically.” uv cache clean removes everything, and uv downloads and builds packages again as it needs them.

A clone is an APFS copy that, Apple says, “occupies no additional space on disk”: both files share the same blocks until one of them changes. A hard link is a second name for the same file. Either way, a node_modules folder from pnpm or Bun, or a virtual environment from uv, looks as big as a full copy, but its package files share their data with the store or cache. Deleting the folder frees only the part no other file shares. The rest is freed only when nothing else, such as the store, the cache or another project, still uses it. pnpm’s FAQ explains the hard-link case: “that 1MB is the same space on the disk addressed from two different locations.”

Rust build folders

Cargo builds into a folder named target at the root of each project, so every project, and every worktree of one, has its own. Cargo cleans up its download cache on its own, but not target.

  • Run cargo clean in a project to delete its target folder. cargo clean --dry-run shows what it would delete. The next build compiles everything again.
  • ~/.cargo/registry holds the crates Cargo downloaded: compressed .crate files in registry/cache and their unpacked sources in registry/src. When you build, Cargo deletes files there it hasn’t used in 3 months, or in 1 month for files it can make again without a download. It skips this when it runs offline.

Browsers and models

Playwright
Playwright downloads Chromium, Firefox and WebKit to ~/Library/Caches/ms-playwright, and its docs say they take a few hundred megabytes.Playwright deletes a browser version once no Playwright installation on your Mac needs it. npx playwright uninstall removes the browsers of the installation you run it from, and adding --all removes every installation’s. npx playwright install downloads them again.
Hugging Face
Models and datasets you download with Hugging Face’s libraries go in ~/.cache/huggingface/hub, unless HF_HOME or HF_HUB_CACHE points somewhere else.hf cache ls lists what’s there. hf cache rm and a repo ID, such as model/bert-base-cased, deletes one, and hf cache prune deletes revisions no branch or tag uses and unfinished downloads. Add --dry-run to see what either would delete. Version 1.0 of the huggingface_hub library removed the older huggingface-cli command, so guides that use huggingface-cli delete-cache are out of date.
Ollama
Ollama keeps models in ~/.ollama/models, or the folder the OLLAMA_MODELS variable names.ollama ls lists your models, and ollama rm and a model’s name deletes one. ollama pull downloads it again.
LM Studio
LM Studio’s docs show its models in ~/.lmstudio/models, in a folder for each publisher and model. You can change that folder in its My Models tab.lms ls lists each model with its size, and the total. LM Studio’s docs don’t describe a command to delete a model.

Advice to skip

  • Deleting a worktree’s folder in Finder. Git keeps its record of the worktree until git worktree prune clears it, and the branch stays. Conductor’s changelog asks: “please do not move or delete workspace or repo directories outside Conductor.” Use git worktree remove, or the tool’s own archive or delete.
  • Deleting a project’s .git folder to shrink it. The workaround in the Codex issue labels rm -rf .git && git init “Nuclear.” It deletes every commit, branch and stash that exists only on your Mac. git gc, above, removes only objects nothing points to.
  • Deleting files inside a package store or cache by hand. uv’s docs say “it’s never safe to modify the cache directly,” such as by removing a file or folder. Use the tool’s own command, such as pnpm store prune, bun pm cache rm or uv cache clean.
  • Deleting ~/.claude or ~/.codex. Next to transcripts, they hold your settings and can hold your sign-in. Claude Code’s docs say not to delete ~/.claude.json, ~/.claude/settings.json or ~/.claude/plugins, which “hold your auth, preferences, and installed plugins.” Use claude purge or codex delete instead.

How to see yours

  1. In Sizewise, choose File > Scan Folder and choose your home folder, or scan your whole disk to see these folders next to everything else.
  2. Lock a folder with a click to see what deleting it would free. When that’s less than its size, Sizewise shows what keeps the rest, such as copies that share their data.
  3. Scan the same folder again next week, and if it grew a lot, a strip over the map names up to three places where the space went.

Sizewise shows where the space is, and you decide what goes. It asks before every move, and moves files only to the Trash, so you can put them back.
